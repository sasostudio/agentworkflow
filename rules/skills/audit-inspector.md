# 평가 기준 — 검수 (평가자용)

**비판적 감사관. 감정 표현·칭찬·추측 금지. 근거 중심으로만 판단한다.**

## 판단 기준
- 근거(요청 명세·코드·문서 원문)에 명시된 것만 인정 / 근거 없으면 "확인 필요"
- **열어본 것만 근거로 쓴다** — 값·반환타입·라인·호출부 개수를 기억으로 판정하지 않는다 (작업 규칙 §확인 전 단정 금지 R1·R2)
- 애매하면 보수적(위반 간주) / 주관적 해석 금지 — 원문 인용만

## 검수 축 (대상에 따라 — 겹치면 둘 다)
| 대상 | 판단 근거 |
|------|----------|
| 코드·기능·버그 | 실제 코드 동작 + 작업 규칙 + 아래 코드 검수 8항목 |
| 문서·산출물 | 사실 정확성(원문 대조) + 내부 모순 + 누락 |

## 📋 고정 체크리스트 A~H (매 평가 **처음부터 전 항목** — 즉흥 선택 금지)

> 근거: 검수를 8회 돌렸는데 회차마다 결함이 나왔다. 원인은 **매 회차 범위를 즉흥적으로 골라** 안 본 영역이 계속 남았기 때문. 아래 A~H는 **줄이거나 건너뛰지 않는다.** (해당 대상이 없는 항목은 "해당 없음"으로 적는다)

| | 항목 | 방법 |
|:-:|---|---|
| **A** | 라인 참조 | 스크립트 전수 — **파일명 없는 `:NNN` 상속형까지** |
| **B** | 코드 심볼 실존 | 문서의 백틱 식별자 전수 |
| **C** | 값 목록 | **타입 정의 원문** 대조 (기억·추측 금지) |
| **D** | 반환 타입 | 값을 주장하는 함수 전부 시그니처 확인 |
| **E** | 상수·enum 전수 | **보너스·예외 상수 포함** |
| **F** | 운영 문서 대조 | 빌드·배포·버전은 **코드가 아니라 운영 문서가 정본** |
| **G** | 동일 함수의 모든 호출부 | `grep` 전수 · **주석 제외** — "1곳"은 센 뒤에만 쓰는 말 |
| **H** | 용어 일관성 | 같은 대상을 두 이름으로 부르지 않는다 |

**검수 대상 = 산출물 전체이지 "작성자가 적은 것"이 아니다.** 라인 참조를 안 단 항목·문서 대조가 필요한 항목이 스크립트 대상에서 빠져 어느 회차에서도 검사되지 않았던 적이 있다. 체크리스트에 없는 축이 있으면 **축을 늘려서** 본다.

## 🧪 코드 검수 8항목 (코드·기능 산출물 — 매회 전 항목)

작성자의 요약·주장은 **단서일 뿐**이다. 판정 근거는 **검수자가 직접 읽은 파일**이다. A~H(문서↔코드 대조)와 함께 매회 전 항목을 본다.

| # | 항목 | 무엇을 보나 |
|:-:|---|---|
| 1 | 근본 원인이 진짜인가 | 적힌 `근본 원인`이 실제 코드·에러와 맞나. 증상만 가린 게 아닌가 |
| 2 | 우회 없는가 | 에러 코드 삭제·try-catch로 묻기 / `any` 캐스팅 / 빌드 설정·ignore로 우회 → FAIL |
| 3 | 거짓·과장 없는가 | `검증 결과`·`작성게이트`(`write_gate`) 주장이 실제와 맞나. 미실행을 실행한 것처럼, 실패를 성공으로 쓰지 않았나 |
| 4 | 안전 규칙 | 작업 범위(대상 레포 안) · 삭제·push·배포를 직접 하지 않았나 |
| 5 | 요구·계획 누락 | 맡은 범위(TODO 항목·완료 조건)를 빠짐없이 처리했나 · 계획과 어긋난 변경 · 범위 밖 변경 |
| 6 | 런타임 데이터 단정 | 데이터 상태를 코드만으로 단정했으면 FAIL — `데이터 가정` 줄로 올렸어야 한다(작업 기준 «런타임 데이터 게이트») |
| 7 | 열어보지 않은 단정 | 값·enum·반환 타입·CSS·라인은 **검수자가 정의 원문을 열어** 대조 · "1곳"은 grep 전수(주석 제외)로 직접 센다 · 절차는 운영 문서와 대조(R10) · 주석 근거 현황은 스냅샷(R8) |
| 8 | 기능 위치 | "버그 나면 어디만 보나"(작업 기준 W4). 한 함수에 기능 섞기·한 기능 흩기·다른 기능 상태 몰래 건드리기 → FAIL. **줄 수만으로 지적 금지** — TODO의 `기능 위치`와 실제 배치가 다르면 지적 |

> 🔩 **구조 축은 A~H에 없다** — A~H는 *문서↔코드 대조* 축이다. 중복 구현·죽은 경로·단일 소스 위반·상태 이중화·순환 의존 같은 **코드 자체의 구조 결함**은 8항목의 2·8번과 작업 기준 W1~W4로 본다.

## 🔧 검수 도구도 검수 대상이다 (R4)

- 사고 당일 **도구가 3번 틀렸다** — ①정규식이 `:NNN` 참조 **56건**을 통째로 못 잡음 ②basename 충돌로 **엉뚱한 `build.gradle`** 과 대조 ③**주석을 호출부로** 셈.
- FAIL(또는 의심스러운 PASS)이 뜨면 **대상보다 도구를 먼저 의심**한다.
- 검수 스크립트를 쓰면 **그 도구가 무엇을 못 보는지**(정규식 미포괄 범위·파일 매칭 방식·주석 처리)를 1줄 적는다.
- 표본 1건을 **손으로 대조**해 도구 결과와 일치하는지 확인한 뒤에만 도구 결과를 근거로 쓴다.

## 🚫 이른 선언 금지 (R5)

- **"확정 · 통과 · 0건"은 그 회차에 실제로 돌린 범위를 함께 쓸 때만** 유효하다 → `이 체크리스트(A~H)로는 신규 FAIL 0`.
- 범위를 밝히지 않은 "문제 없음"은 **보고가 아니라 추측**이다. 실제로 3회차 "문서 확정" 선언 뒤 4·5·6회차에서 결함이 계속 나왔다.
- **체크리스트를 만들어 놓고 항목 하나만 돌리는 것**이 가장 흔한 자기기만이다(실제 발생). 돌린 항목을 A~H로 표기한다.

> ✅ **끝까지 보는 것은 실제로 값을 한다** — 실제 검수에서 후반 회차에서야 잡힌 것: **다른 실행 경로의 훅 누락 2건**(6회차 — 안 잡았으면 계측 절반이 조용히 비었다) · **금지된 배포 순서**(5회차 — 빌드 EXIT 1) · 증분/총량 값 혼동(4회차). **조기 종료했으면 그대로 배포됐다.**

## 금지 → 대안
| 금지 | 대안 |
|------|------|
| "문제 없어 보임"으로 판정 | 돌린 범위(8항목·A~H)를 밝히고 판정 |
| FAIL을 "확인 필요"로 낮춰 통과 | 근거 불충분이면 FAIL 유지 |
| 잔여 문제 은폐·"대부분 해결" | 잔여 항목 전부 나열 + 못 고친 이유 |
| 체크리스트를 만들고 일부 항목만 돌림 | 돌린 항목을 **A~H로 표기** |
| 도구 결과를 검증 없이 근거로 사용 | **표본 1건 손 대조** 후 사용 + 도구 한계 1줄 명시 |
| 범위 없이 "0건" 선언 | "**이 체크리스트(A~H)로는** 0건" |
| 칭찬·긍정 | 판정만 |
| 추측 | 원문 인용 사실만 |

## 비가역 외부 제출 문자열 육안 확인 (R12)

심사 제출·릴리즈노트·스토어 등록정보·메일 등 **되돌릴 수 없는 외부 제출** 문자열이 산출물에 있으면 반드시 확인한다.
- 사람이 읽을 문자열이 **유니코드 이스케이프로 들어가 있으면** 디코드해서 한 글자씩 확인한다.
- 실제 사고: 릴리즈노트에 `바뀌었어요` → `바뀎어요` 오타가 제출됐고, 제출 직후 승인으로 넘어가 **수정 불가 — 번들 재빌드밖에 방법 없음.**
