## 🔒 확인 전 단정 금지 게이트 (전 단계 상시 — 작업 규칙 §확인 전 단정 금지 R1~R12)

**"열어보지 않고 쓰지 않는다."** 하루 사고 23건이 전부 이 하나에서 나왔다.
아래는 코드·문서·보고 **문장을 쓰기 직전** 스스로 돌리는 체크다. 비용은 정의 1~9줄.

| 쓰려는 문장 | 쓰기 전에 반드시 |
|---|---|
| 값·enum·상태 이름 (`'A'`, `'draw'` …) | **타입/상수 정의 원문 열기**. 안 열었으면 "미확인" (R1) |
| "이 함수는 X를 반환한다" | **시그니처 1줄 확인** (R1) |
| "여기 1곳만 고치면 된다" | **`grep` 전수 세기(주석 제외)** — "1곳"은 센 뒤에만 쓰는 말 (R2) |
| 기존 클래스·상수 재사용 | **원본 CSS/정의 열기.** 이름이 비슷한 건 근거가 아니다 (R7) |
| 파일:라인 참조 | 파일을 열어 **대조** (R1) |
| "지금 이렇게 동작한다" (주석 근거) | 주석은 **작성 시점 스냅샷** — 운영 문서·실측으로 확인 (R8) |
| 빌드·배포·버전 순서 | **운영 문서가 정본** (코드 아님) (R10) |
| "이건 아직 안 했다" (할 일·테스트 목록) | **완료 기록 열기.** 커밋 시각 ↔ 빌드/번들 시각 대조 (R11) |
| 날짜·요일 | 계산해서 확인, **날짜+요일 함께** 적기 (R9) |
| 외부에 나가는 사람이 읽을 문자열 | **이스케이프로 넣지 않는다.** 넣었으면 디코드해 육안 확인 (R12) |
| 런타임 데이터 상태 (DB 문서·배포 반영·시드·계정 상태) | **코드만 보고 단정하지 않는다.** 아래 «런타임 데이터 게이트» (R1의 데이터판) |

### 런타임 데이터 게이트
- 코드에 없다고 데이터에도 없는 게 아니다. **"코드에 없으니 실유저다"류 추론이 대표 함정**이다 — 잔여 시드 문서·수동 생성 데이터는 코드 밖에 있다.
- 결론이 런타임 데이터에 기대면 단정 대신 **`데이터 가정: (가정) — 확인 방법: (콘솔·쿼리 경로)`** 한 줄을 결과 요약에 남기고, 확인이 필요하면 방향 질문(`question`)으로 올린다.
- **코드 검수로는 이걸 못 잡는다** — 검수자도 코드만 보기 때문이다. 그래서 작성자가 올려야 한다.

> 🚨 **규칙을 적는 것과 지키는 것은 다르다.** 사고 당일 회고를 쓴 **직후 답변에서 또 어겼다.**
> 유일하게 효과 있는 건 **문장 단위 자문** — *"이 문장의 근거를 내가 열어봤나?"*

## 🔨 작성 게이트 (코드를 쓰기 직전 상시)

**"쓰기 전에 찾아본다."** 위 게이트가 *"열어보고 말해라"*면, 이건 *"열어보고 써라"*다.

AI가 만든 코드는 포맷이 깔끔하고 주석도 잘 달려 **리뷰를 통과한다.** 정작 문제를 만드는 건 중복 구현·경로 병존·이중 소스인데, 겉이 매끈할수록 안 보인다(GitClear 2026 실측: 5줄 이상 블록 중복이 2년 새 **8배**). 이 결함은 쌓인 뒤 걷어내는 것보다 **작성 시점에 막는 것이 압도적으로 싸다.**

| | 코드 쓰기 직전 자문 | 통과 조건 | 막는 것 |
|:-:|---|---|---|
| **W1** | 같은 일을 하는 코드가 **이미 있나?** | `Grep`/`Glob`으로 **찾아본 뒤에만** 새로 쓴다. 있으면 재사용·확장. "없을 것 같다"는 근거가 아니다(R2와 같은 논리) | 중복 구현 |
| **W2** | 새 경로를 만들면 **구 경로를 같은 작업에서 제거**하나? | 신·구 병존 금지. 삭제는 직접 하지 않으므로, 못 지운 구 경로는 **이유와 함께 요약에 1줄** 남긴다. 병존을 남기면 다음 작업자가 한쪽만 고친다 | 죽은 경로·경로 병존 |
| **W3** | 이 값이 정의·저장되는 곳이 **여기 하나뿐인가?** | 상수·수치·URL·상태는 단일 소스. 둘째 사본을 만들려면 첫째를 없앤다 | 단일 소스 위반·상태 이중화 |
| **W4** | 이 기능에 버그가 나면 **어디만 보면 되나?** 바로 답할 수 있나 | 기능마다 자기 함수·구역을 가진다. 한 함수에 여러 기능을 섞지 않고, 한 기능을 여러 곳에 흩지 않고, 다른 기능의 상태를 몰래 건드리지 않는다. **파일 분리는 한 파일에 기능이 많이 쌓여 찾기 어려울 때만** — 줄 수는 기준이 아니다 | 디버깅 시 전체를 다 봐야 하는 구조 |

**결과 1줄 (생략 금지)** — 결과 JSON `write_gate` 칸에 적는다. 평가자가 코드와 대조한다.
- 실행: `W1 grep 3건 → 기존 useMatch 재사용 / W2 구경로 1개 제거 / W3 통과 / W4 useMatch.ts의 settleMatch()에 둠`
- 해당없음: `해당없음 — 신규 코드 0줄(CSS 값만 변경)`

> **축소 적용 금지** — "간단한 수정이라" 건너뛰지 않는다. W1은 `grep` 1회로, 비용이 정의 원문 열기와 같다.

## 작업 방식

1. 요구사항(TODO 항목·완료 조건)을 1줄로 정리하고 **검증 가능한 성공 기준**을 확인한다.
2. 영향받는 파일을 전부 나열한다. 다중 파일이면 읽기 먼저 → 수정 나중. **수정·훅 지점은 호출부 grep 전수 후에만 확정(R2).**
3. 구현한다. **값·타입·반환·CSS·상수는 정의 원문을 열고 쓴다(R1·R7).** 코드를 쓰기 직전 작성 게이트 W1~W4.
4. 빌드/실행/자기 검사로 검증한 뒤 보고한다. 못 하면 "검증 불가"를 명시한다. **"통과·0건"에는 실제 돌린 범위를 함께 적는다(R5).**
5. 버그는 근본 원인 → 수정 → 1줄 보고(`근본 원인:`).
6. 성능 최적화는 개선 전후 숫자로 비교한다.

## 코딩 원칙
- Clean Code, DRY, 성능 우선
- 주석은 왜(Why)만 설명
- **단순함 우선** — 요청한 문제만 최소 코드로 해결. 요청 안 한 추상화·추측성 기능·"유연성" 금지
- **수술적 변경** — 요청과 무관한 코드·주석·포맷은 건드리지 않는다. 변경한 모든 줄은 요청에 직접 추적돼야 한다
- **복잡 로직 검증 먼저** — 점수·밸런스·상태머신은 가능하면 검증/테스트 케이스를 먼저 정의 후 구현
- **미확인은 "미확인"이라 쓴다** — 값·반환·스타일·호출부 개수를 추측으로 적지 않는다 (위 게이트)
- 근본 원인 우선 — 우회/증상제거 금지 (에러 삭제·any 캐스팅·빌드설정 우회 금지)
- 해결책 적용 전 부작용 검증(다른 기능 영향·기존동작 보존·사이드이펙트·재발가능성)
